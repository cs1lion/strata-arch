## 瓶颈（记录，不当作已证明的根因）

每键改 query 都会触发一次 `cx.notify()`，下一帧走完整 `MapView::render`：

- 克隆整个 map（802 节点 + 4363 边）；
- 重建 4363 个 `EdgeDraw`（票 10 的 A 只合并绘制，不减少逐边构造）；
- 重建 `stage_of_layer` BTreeMap；
- 重建 802 个节点元素树与 802 个文本 run。

默认 fit 视图下所有节点都在画面内，票 10 的 B（视口裁剪）可能没有可剪元素；这一点在评估时必须先核实，不作为既定事实。A 默认开启、B 默认开启，输入 p95 仍 48.59ms，说明「已做的批处理 + 裁剪」不足以覆盖输入路径。（**2026-11-09 更正：第一句假设经确定性核对不成立，见文末「事实更正」小节；原文保留，不静默删除。**）

票 10 的受控实验给过可归因的量级（不是本场景的收益承诺，只作评估时的分项参照）：跳过 labels 差值 13.6–17.8ms，跳过 edges 差值 24.7–41.4ms，空场景固定地板 14.7–14.9ms（旧批次、全量平移口径）。这些读数不能直接外推到输入路径，评估时必须用 `-Mode search` 重新测。

## 三条候选路线

### A. 脏区重绘

**改动面:** 把「场景」与「搜索面板/标签」拆成可独立失效的两层；输入期间只重建面板，场景层保持上一帧内容。需要明确失效条件：相机变化、揭示、淡出、下钻、缩放、窗口尺寸、DPI、主题。若 GPUI 0.2.2 没有公开的局部重绘/damage region 入口，本路线会退化为「缓存场景元素树」或不可行；这一点必须先验，不能在实现阶段才发现。

**预期收益:** 不作数值预测。定性上，输入期间每键的工作量应从「重建 802 节点 + 4363 边 + 802 标签」降到「重建面板」；但 GPUI 仍会合成整窗，旧受控实验的空场景地板 14.7–14.9ms 说明固定成本仍在。能否进 33ms 只能实测。

**风险:** 局部失效漏判会出现残影/撕裂（相机、淡出、揭示、Esc 复原各是一条路径）；面板与场景的层级、命中测试、裁剪顺序可能改变；若没有公开局部重绘入口，改动面会膨胀成离屏缓存。

**判据怎么定:**

1. 性能：同一 `eval/frame-timing.ps1 -Mode search` 口径，语料、81 键、1ms/键、79 个间隔不变；连续 3 次独立运行，每次独立计算 p95，**3 次 p95 的最大值 ≤33ms**（最坏一次达标），同时报 median/min/max。判据不沿用「接近即可」。
2. 脏区正确性：输入前后的场景区域（面板矩形之外）**逐像素 0 差异**；面板区域内允许变化。像素口径用现有 `map-pixel-compare.ps1` 的通道差 >6，比较区域按面板矩形扣除。
3. 失效正确性：相机平移/缩放、揭示结束、淡出开/关、`Enter` 聚焦、`Esc` 清除、下钻、窗口 resize、DPI 变更后，各抓一帧与无缓存基线比较；有变化的只允许是这些操作本身应有的变化，缓存不得残留上一状态。
4. 回归：票 20 的 C1–C7、C9、C10 全绿；`cargo test --workspace`、`cargo fmt --all --check` 干净；`eval/pixel-evidence.ps1` 24/24。
5. 失败判据：任一 p95 >33ms；面板外出现非零像素差；任一失效路径出现残影/上一状态；为达标改动 C8 的 33ms 或像素闸门；引入第二套与 GPUI 分叉的渲染路径而未按票 10 的「共享场景 IR」约束登记。

### B. 离屏缓存

**改动面:** 把场景预绘制成可复用的缓存（元素树、文本排版结果或纹理），输入期间直接合成；相机/缩放/DPI/尺寸/淡出/揭示变化时重建。必须先解决 API 可行性：`gpui 0.2.2` 无公开离屏导出入口（已写入 `docs/acceptance-gaps.md` 2.2 与 `AGENTS.md` 事实边界）。可走的只有三条：(1) 缓存元素树/文本排版而非像素；(2) 改用 gpui git revision 取得离屏 API；(3) 另建 CPU 光栅器。后两者分别破坏 `=0.2.2` + `--locked` 固定策略、或形成第二条渲染路径，均需单独决策，不在本票默认范围。

**预期收益:** 不作数值预测。理论上限是「场景重建成本」归零，只剩合成与面板；实际受固定合成地板、缓存失效频率、纹理上传/显存带宽影响，必须实测。若只能缓存元素树而不能缓存像素，收益可能只覆盖布局/排版的一部分。

**风险:** 版本 pin 与 `--locked` 策略被破坏；第二套渲染路径漂移；纹理/缓存的内存与显存上限未定；DPI/resize 下缓存尺寸与清晰度；揭示/淡出期间缓存每帧失效，反而更慢；GPUI 0.2.2 的公开 API 可能根本不支持所需缓存粒度。

**判据怎么定:**

1. 可行性前置判据：先证明存在**不改变 `gpui = "=0.2.2"` 与 `--locked`** 的公开 API 路径，能缓存所需粒度；证明不了就以「不可行」关闭本路线，附源码检索与最小复现，不得先写实现再解释。
2. 若可行，性能判据同 A 第 1 条（3 次 p95 最大值 ≤33ms）。
3. 视觉：静止帧（默认 fit、两个缩放位）与无缓存基线**逐像素 0 差异**；输入期间面板外 0 差异；揭示/淡出结束态 0 差异。
4. 失效：相机、缩放、resize、DPI、主题、下钻、淡出/揭示各路径重建一次后与基线一致；缓存不得跨状态复用。
5. 资源：缓存内存/显存峰值有上限并归档读数；不得用「未测内存」换帧率。
6. 失败判据：破坏版本 pin 或 `--locked`；需要第二条渲染路径却未按共享 IR 约束登记；任一 p95 >33ms；静止帧有像素差；缓存失效漏判；内存/显存无读数。

### C. 输入态降格

**改动面:** 只在 `SearchMode::Input` 期间降低绘制细节（标签、边，或两者），复用现有 `STRATA_RENDER_SKIP` 类机制；面板内显示明确的「输入期间简化显示」标记；`Enter` 聚焦、`Esc` 关闭、空命中回车等离开输入态时立刻恢复完整绘制。`Focused` 与 `Closed` 不受影响。

**预期收益:** 不作数值预测。票 10 的受控差值显示 labels/edges 是可归因的大头，但那是平移口径、旧批次；输入路径必须分别测「只跳 labels」「跳 edges + labels」两档，看哪一档先到 33ms，测不到就如实报剩余。

**风险:** 输入期间画面与最终态不一致，用户可能误读；降格标记必须可见且文案明确；离开输入态若恢复不彻底会污染聚焦态或清除态；只跳 labels 可能仍不达标，跳 edges 又可能让地图在输入时失去结构信息；像素证据的「输入态」帧会与既有基线不同，必须把「有意降格」和「渲染缺陷」分开登记。

**判据怎么定:**

1. 性能：同 A 第 1 条（3 次 p95 最大值 ≤33ms）；另分别报「只跳 labels」「跳 edges + labels」两档的 median/p95，证明达标的是哪一档。
2. 最终态等价：`Enter` 聚焦后与 `Esc` 清除后各抓一帧，必须与不降格的同状态基线**逐像素 0 差异**；输入态允许与基线不同，但只允许出现在声明的降格元素上。
3. 状态隔离：模型断言 `Input` 之外（`Focused`/`Closed`）不得带降格标志；离开输入态同一帧恢复；面板降格标记只在输入态可见。
4. 可解释性：降格标记文案与 README/票内说明一致；像素证据新增「输入态降格」帧时，报告里必须写明这是产品行为，不是回归。
5. 失败判据：任一 p95 >33ms；最终态与基线有像素差；降格泄漏到聚焦/关闭态；标记不可见或文案缺失；为达标把 33ms 改成更宽的值。

## 事实更正（2026-11-09）：B 在默认相机下并非无可剪元素

**被推翻的原假设**：上文「瓶颈」段第一句「默认 fit 视图下所有节点都在画面内，票 10 的 B（视口裁剪）可能没有可剪元素」。原文保留在上面，不删除；推翻理由如下。

**核对方法（确定性，不用计时读数，避开票 10 记录的 32% 批次漂移）**：

- 命令：`target/debug/arch-view.exe scene tests/corpus/excalidraw --out <scene.json>`；产物 `layout.width=1200`、`layout.height=6184`，**802 节点 / 4363 边 / 6 层带**，节点 y 范围 34 .. 6174。
- 相机与窗口：`CanvasState::new` 用 `Viewport::default()`（zoom 1 / pan 0，`crates/arch-view/src/view.rs:412`）；`map` 窗口 `Bounds::centered(... 1200×800)`（`main.rs:420/672/1222`）；`eval/frame-timing.ps1 -Mode search` 只设 `STRATA_PHASE_MARKERS` / `STRATA_FRAME_TRACE`，**不设** `STRATA_EVIDENCE_VIEWPORT`；像素比较默认相机同为 `default=0,0,1`（`eval/map-pixel-compare.ps1:38`）。
- 判据照抄 `view.rs:141-146` `rect_fully_outside`（margin 2.0）与 `segment_fully_outside`。

| 视口 | 完全在外的节点 | 完全在外的边 |
| --- | --- | --- |
| 1200×800（测量口径） | **702 / 802** | **3603 / 4363** |
| 1200×760 | 709 / 802 | — |
| 1100×760 | 709 / 802 | — |
| 1000×700 | 716 / 802 | — |

**结论**：B 不是空操作，约 87.5% 节点、82.6% 边在默认相机下被剪掉。因此「每键重建 802 节点 + 4363 边的元素树」只对**整份 map 克隆与 `stage_of_layer` BTreeMap 重建**成立，对元素树构造不成立；每键实际元素构造约 100 节点 + 760 边，外加 GPUI 合成固定地板（票 10 记录 14.7–14.9ms）。

**影响范围**：仅修正瓶颈描述与收益预估口径；不改本票任何判据、不改 33ms、不改 `proposal-only` 状态、不新增门禁。三条候选路线的可行性结论与判据保持不变。若要量化路线收益，仍需 `-Mode search` 分项实测；两批顺序比较不可判定（票 10 的 32% 漂移），需输入态同进程交替测量，属 `eval/` 改动，须独立提交并附旧/新读数与理由。

## 路线 A 实测（2026-11-11）：判据不成立，实现已回退

**原判据照抄、未改**：本文路线 A 第 1 条「连续 3 次独立运行，每次独立计算 p95，**3 次 p95 的最大值 ≤33ms**」；本文「共用回归」段「失败一律如实报剩余，不调阈值、不改判据、不静默删除本票或票 20 的 C8」。判据与本票 `proposal-only` 状态均保持不变。

**验收五要素**

1. 命令：`pwsh -File eval/frame-timing.ps1 -Mode search -SearchPrefix "/componentscomponentscomponentscomponentscomponentscomponentscomponentscomponents" -SearchKeyDelayMs 1 -OutJson <每次独立文件>`；实验开关 `STRATA_SCENE_CACHE=1`（默认关闭）；同会话按 `ON,OFF,ON,OFF,ON,OFF` **交替**跑，避免票 10 记录的批次漂移；`pwsh -File eval/pixel-evidence.ps1 -OutDir out/pixel-evidence-t21-cache`。
2. 固定样本/环境：`tests/corpus/excalidraw`（802 模块 / 4363 边 / 6 层带）、release 构建、81 键 / 1ms 每键 / 79 个间隔、Windows。
3. 期望读数或行为：3 次 ON 运行 p95 最大值 ≤33ms；面板外像素 0 差异；`eval/pixel-evidence.ps1` 24/24。
4. 失败判据：任一 p95 >33ms；缓存子视图出现残影/上一状态；回归测试变红；为达标改 33ms。
5. 自动化状态：性能与像素均为本机脚本实测（需可见桌面会话，不进 CI）；三次独立运行 + 交替 OFF 对照 + 原始 JSON 全部归档。

**实现**：`AnyView::cached(StyleRefinement::default())` 把场景元素树放进 `MapView` 的 `cached` 子视图；用场景指纹（相机、选中、聚焦、播放、揭示、调优、视口尺寸）在状态变化时强制重绘。探针已证明通知根视图不会标脏子视图，故输入期可复用。

**读数（原始 JSON：`out/t21-c-summary.json`、`out/t21-c-on-*.json` / `off-*.json`）**

| 交替序 | 状态 | 间隔数 | median | p95 | min / max |
| --- | --- | --- | --- | --- | --- |
| 1 | ON | 79 | 33.07ms | **33.84ms** | 24.12 / 34.02 |
| 1 | OFF | 81 | 32.36ms | 34.18ms | 7.21 / 38.84 |
| 2 | ON | 79 | 32.95ms | **33.93ms** | 24.55 / 34.26 |
| 2 | OFF | 82 | 32.85ms | 33.74ms | 8.55 / 34.54 |
| 3 | ON | 80 | 33.05ms | **33.91ms** | 9.58 / 34.10 |
| 3 | OFF | 79 | 33.14ms | 33.81ms | 24.76 / 34.90 |

- **ON 三次 p95 = 33.84 / 33.93 / 33.91ms，最大值 33.93ms > 33ms → 判据不成立（红）。**
- **ON 与 OFF 无差别**：ON 最大 33.93ms vs OFF 最大 34.18ms，中位数 33.0 vs 32.8ms。交替对照下的差值在噪声量级，缓存收益**不可判定**。因此不得把票 20 的 48.59ms 与本轮 33.9ms 当作「优化收益」比较——那是两批不同会话，票 10 已记录同机批次漂移可达 32%。
- **缓存确实命中，不是没生效**：`out/t21-raw-hitcheck-on.txt` 实测 `phase: scene:cache` **83** 次、`phase: scene:render` **3** 次（约 96% 输入帧复用了 layout/paint）；关闭时 `scene:cache` **0** 次（`out/t21-raw-hitcheck-off.txt`）。
- 视觉正确：`eval/pixel-evidence.ps1` 开启缓存后 **passed=24 failed=0**（`out/pixel-evidence-t21-cache/report.json`），搜索三态、聚焦、清除、diff 三色、P1/P3 均无残影。

**结论与推翻理由**：缓存场景元素树在视觉上正确、在机制上确实复用，但**没有带来可分辨的帧时间收益，也未达 33ms**。可解释原因：① 默认相机下 B 已剪掉 702/802 节点、3603/4363 边（见上节事实更正），待缓存的元素树本就很小；② GPUI 仍合成整窗，票 10 记录的空场景固定地板 14.7–14.9ms 不受元素树缓存影响；③ 本轮 OFF 基线已约 33ms，接近判据边界。按本文「失败一律如实报剩余」与票 10「两轮 diff 优化均回退」的先例，**该实现已回退**，`crates/arch-view/src/main.rs` 与 `e94dab8` 完全一致；实验补丁留档 `out/ticket21-feasibility/route-a-experiment.patch`（`out/` 被 `.gitignore` 排除）。

**已知偏差（单列）**：本轮 OFF 基线 p95 约 33.8ms，与票 20 同语料同命令记录的 48.59ms 相差约 30%，与票 10 记录的 32% 批次漂移同量级。这说明 33ms 这一**绝对阈值**的判定同样受会话环境影响；本轮仍按原判据判红，**不改阈值、不改判据**，也不据此宣称任何路线失败或成功。
