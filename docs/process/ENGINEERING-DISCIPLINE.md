# 工程纪律总纲（Engineering Discipline）

本文件是 Strata 项目工程纪律的**唯一入口**。每轮作业开工前按第 9 节取用，收尾前按第 9 节自检。
文中只固定「适用条件 + 判据」，具体操作细节引用分文档，避免出现两套互相矛盾的规则。

- 状态：2026-11-07 定稿，适用于 ticket 02 之后的所有作业；ticket 01 的历史例外见 `docs/process/tdd.md`。
- 分文档权威归属：
  - 分层 TDD 细则：`docs/process/tdd.md`（**唯一**档位定义与汇报模板）
  - 评估体系细则：`docs/process/eval-harness.md`（**唯一**案例分层、指标、门禁）
  - 无法自动验证项的替代口径：`docs/acceptance-gaps.md`
  - 架构裁决：`docs/adr/`

若本文件与分文档冲突，以分文档为准，并立即修正本文件；不得两处各写一套。

## 1. 分层 TDD

档位定义、模板、ticket 对照表全部以 `docs/process/tdd.md` 为准。本节只固定「什么任务用哪档、判据是什么」。

| 档位 | 适用任务 | 硬判据 | 不满足即判红 |
| --- | --- | --- | --- |
| **A 严格红绿** | CLI 契约、模块解析、符号提取与调用图、层推断、路径查询、git 历史指标、图算法 | 先有真实失败的 Red 输出，再实现；测试只断言外部可观察行为；固定 fixture/样本 + golden | 无真实 Red、事后补写红绿、断言私有实现、golden 漂移未说明 |
| **B 断言先行** | GPUI 布局、绘制、交互外观、播放状态、结构断言 | 实现前先给断言清单并映射到可见行为；结构断言开启；像素门禁默认关闭 | 为过测试迁就实现、放宽阈值、删断言；无法出示「断言先于实现」证据 |
| **C 预算先行** | 性能、内存、帧时间、启动时限、墙钟 | 实现前钉死指标/阈值/命令/样本 commit/次数/硬件；读数必须实测 | 先看读数再调阈值；用估算替代实测；无原始输出 |
| **不适用** | 人工可用性测试（ticket 12）、占位票（ticket 13）、纯文档改动 | 人工协议 + 证据归档，或只交占位文档 | 给不适用项伪造自动化红绿 |

补充判据：

- 一张票可跨档（如 03 = A + B、07 = B + C），但**每档分别交证据**，不能合并成一句「测试通过」。
- A 档一个 Red 只加一个失败断言；Red 命令与 Green 命令必须一致，便于对照。
- B 档「断言先于实现」的证据可以是提交顺序、测试文件先行清单或时间戳记录；口头声明不算。
- C 档默认 3 次运行，记录每次读数、中位数与 p95，并附硬件信息；只跑 1 次不算。
- 任何档位都不得在看到结果后回改判据；确需改判据，走第 7 节。

## 2. 验收标准制度

每张 ticket 必须同时包含以下五项，缺一项即视为未定义完成，不得进入实现：

1. **命令**：可复制执行的完整命令（含包名、测试目标、参数）。
2. **固定样本/commit**：fixture 路径，或样本仓名 + 锁定 commit（与 `docs/process/eval-harness.md` 的 pin 约定一致）。
3. **期望读数或行为**：具体数字（分母可见）、边集合、文件集合或可观察状态。
4. **失败判据**：哪些情况算失败（缺边、多边、错归属、计数漂移、悬空边、非确定性、超预算等）。
5. **自动化状态**：`已自动化` / `部分自动化` / `未自动化（已登记替代口径）`。

禁止：

- 「功能正常」「性能良好」「体验流畅」这类无法判定的描述。
- 只给百分比不给分母；只给汇总不给失败项。
- 把未自动化的项藏在「手工验证过」里；必须显式登记到 ticket 与 `docs/acceptance-gaps.md`。
- 期望值写「约」「大概」「预计」。未实测就标「未验证」，不写预期值。

验收标准本身有歧义时：停下来向用户报告并确认，不自行解释成对自己有利的版本。

## 3. 评估体系

案例分层、5 个固定指标、仓内/仓外分工、SHA256 防作弊、提交级快集与发布级全集，全部以 `docs/process/eval-harness.md` 为准。执行时至少要满足：

- **三层案例**：L1 人工标注集（算精确/召回）、L2 真实仓库快照（只回归不判对错）、L3 合成极端构造（边集合即期望）。
- **5 个指标**：解析召回、解析精确、未解析边数（分原因）、不变量违规数、确定性与资源。每个指标必须带分母与逐条失败项。
- **仓内/仓外**：脚本、标注、合成用例、golden、`eval/baseline/current.json` 入仓；样本仓库本体、完整产物、截图、归档放仓外缓存。
- **SHA256 防作弊**：标注、`expected.json`、golden、pin 清单全部钉 SHA256，清单入仓并由 CI 校验；实现者不得单方面修改期望值。
- **两级门禁**：提交级快集 ≤30 秒（合成 + 小标注 + fixture 不变量 + 确定性）；发布级全集手动/打标触发，跑全部案例 + 两个真实仓 + 资源读数。

修改 `eval/` 下任何期望值 → 见第 6 节提交纪律，必须独立提交并说明旧读数、新读数、理由。

## 4. 流程链（Matt skills）

技能统一安装在仓库内 `.trae/skills/`（已存在 27 个技能目录 + `README.md`），随仓库版本化，不依赖个人全局安装。

| 环节 | 输入 | 产出 | 是否必须用户拍板 |
| --- | --- | --- | --- |
| `setup-matt-pocock-skills` | 仓库现状、issue tracker 选择 | `.trae/skills/` 技能就位 + tracker/标签约定 | **是**：首次配置、tracker 与标签体系 |
| `grill-with-docs` | 想法、已有文档、`GLOSSARY.md` | 被追问澄清的问题清单、已裁决决策、术语修订 | **是**：每个未决问题必须由用户回答或明确授权默认值 |
| `wayfinder` | 已裁决决策集 | 实施路线、检查点、风险与依赖顺序 | **是**：路线与检查点 |
| `to-spec` | 决策与路线 | spec 文档（`docs/spec-*.md`） | **是**：spec 定稿 |
| `to-tickets` | 定稿 spec | 带五项验收标准的 ticket 列表 | **是**：拆分与优先级 |
| `implement`（含 `tdd`、`code-review`） | 已批准 ticket | 代码 + 测试 + Red/Green/Refactor 或 B/C 证据 | 否：在批准范围内自主执行；验收歧义或越界时停下 |
| `pr` | 完成的分支/提交 | PR 标题与正文 | **是**：是否 push、是否开 PR |
| `retro` | 已完成工作与读数 | 经验教训、需固化的规则 | **是**：是否把结论写入总纲/ADR |

约束：

- `implement` 必须调用 `tdd` 技能按第 1 节档位执行；完成后用 `code-review` 自审，再进入 `pr`。
- 网络兜底：`github.com:443` 不可达时，技能/规则更新只能通过 `api.github.com` 拉取归档内容落盘到 `.trae/skills/`；不得凭记忆手写技能替代官方内容，也不得跳过版本记录。
- 每环的产出必须落盘（文档、ticket、提交），口头结论不算完成。

## 5. 报告纪律

每轮汇报固定按以下顺序与口径：

1. **结论先行**：一句话说明本轮做了什么、状态（完成 / 部分完成 / 阻塞）。
2. **三档分开**，不得混写：
   - **做到的**：对应 ticket 验收项，给出实测读数。
   - **没做到的**：明确缺口与影响。
   - **未验证的**：有代码/有设计但本轮没跑过的，写清原因。
3. **读数必须来自实测输出**：命令 + 原始读数（或关键片段）必须可追溯；不得用「全部通过」「效果良好」替代。
4. **已知偏差单列**：与预期不符、与旧读数漂移、平台差异，单独成节并给原因。
5. **禁止汇总替代原始读数**：百分比、总计、均值不能替代逐项读数；失败项必须逐条列出。
6. 汇报中涉及文件时给出可点击路径与行号；涉及提交时给出 SHA 与标题。

## 6. 提交纪律

- **按层拆分**：文档 / core 实现 / 视图实现 / 测试与 fixture 分开提交；能独立编译为准。
- **强耦合例外**：确实无法拆分时（例如类型定义与使用方必须同提交才能编译），在提交信息与汇报中写明原因，不得静默合并。
- **实现与夹具不混**：测试、fixture、golden 不得和实现塞进同一提交（A 档的红绿证据按提交顺序体现）。
- **不混文档**：事实更正、判据调整、ticket 状态更新各自独立或与同类文档同提交。
- **不改写历史**：不 amend、不 rebase 已推送提交、不 force push。
- **不擅自远端操作**：未经用户明确指示，不 push、不创建/关闭 issue、不改远端 issue 状态。
- **`eval/` 期望值独立提交**：提交信息以 `eval:` 开头，写明旧读数、新读数、理由与风险；实现改动与期望值改动不得同提交。
- 每次提交前跑该票要求的命令（至少 `cargo test --workspace` 与 `cargo fmt --all --check`），汇报带上最后一次读数。

## 7. 反作弊红线

以下行为一律禁止，发现即回滚并在汇报中登记：

1. 为让读数好看而**下调阈值、放宽判据、删除断言、缩小样本**。
2. 为凑分类比例而**硬塞**模块层；分类必须能追溯到规则或明确原因码。
3. **事后补写** Red/Green 证据，或把实现后补的测试冒充先行失败。
4. 在看到实测读数后**回改判据**却不报告。
5. 用汇总数字掩盖逐条失败项；只报百分比不给分母。
6. 修改标注/golden 期望值让测试变绿。

**判据不成立时的正确动作**：

1. 先停下来，如实报告「原判据无法成立」的事实与证据。
2. 提出可解释的新判据，说明为什么可执行、如何防止退化。
3. **保留原判据与推翻理由**（在 ticket/ADR 中留档），不静默删除旧判据。
4. 经用户确认后再按新判据执行；新旧读数同口径对比。

已发生的示例：03b 的「自有源码 unclassified ≤10%」因 tsx 平铺结构、无层名依据而不成立，改为「每条未分类带原因码 + external 分离 + 反向用例不退化」，原目标与推翻理由保留在 `docs/tickets/arch-tool/03b-layer-coverage.md`。

## 9. 每轮作业取用清单

### 开工前（勾选）

- [ ] 读本文件对应章节（TDD 档位 / 验收制度 / 提交纪律）。
- [ ] 读当前 ticket 的五项验收标准；确认命令、样本 commit、期望读数、失败判据、自动化状态齐全。
- [ ] 确认本轮档位（A / B / C / 不适用），A 档先准备 Red。
- [ ] 确认固定样本与 commit 存在；样本仓缺失时先报告，不静默换样本。
- [ ] 确认工作区状态（`git status`）与最近提交，避免把他人改动混入。
- [ ] 若涉及判据/阈值：先确认是否已获用户批准；未批准不动。

### 收尾前（勾选）

- [ ] 跑 ticket 指定命令，保留原始输出。
- [ ] 跑 `cargo test --workspace` 与 `cargo fmt --all --check`，记录最后读数。
- [ ] 按第 5 节写「做到 / 没做到 / 未验证」三档汇报，附实测读数与已知偏差。
- [ ] 按第 6 节检查提交拆分；确认没有 amend、没有擅自 push/issue 操作。
- [ ] 若改了判据/期望值：确认已单独提交并写明旧读数、新读数、理由。
- [ ] 更新 ticket 状态与证据（若本轮范围包含）。

### 按任务类型快速取用

| 任务类型 | 必读 | 必做 |
| --- | --- | --- |
| 解析器/契约/图算法 | 第 1 节 A 档、第 2 节、`tdd.md` | 真实 Red → 实现 → golden → 抽检 |
| GPUI 布局/交互 | 第 1 节 B 档、`acceptance-gaps.md` 第 2 节 | 断言清单先行 → 结构断言 → 视觉说明 |
| 性能/内存/帧时间 | 第 1 节 C 档、`acceptance-gaps.md` 第 1/3 节 | 预算先行 → 3 次实测 → 中位数/p95 |
| 文档/判据更正 | 第 2、7 节 | 保留旧判据与推翻理由，不静默删除 |
| 提交/推送 | 第 6 节 | 按层拆分、先测后提交、回报 SHA 与远端一致性 |
