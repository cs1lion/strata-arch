## 0. 这套包回答什么问题

它验证一个产品问题，不是验证动画是否“好看”：

> 一个没接触过目标仓库的 TS/JS 开发者，在没有终端、编辑器、浏览器和提示的条件下，能否在 30 分钟内，仅用当前桌面界面完成 5 个架构理解任务；如果不能，失败落在哪个视图、哪类信息或哪段动线上。

具体产出：

1. 每个任务的通过人数与成功率（`k/5`）。
2. 每个任务的耗时中位数（含超时处理口径）。
3. 参与者自评置信度与实际对错的校准表。
4. 按视图归因的失败清单：地图、下钻、路径、演化时间线、diff。
5. 可复核的原始答案、录屏时间戳和归因证据。

**重要：** 5 人、每题 `≥4/5` 是产品门槛，不是统计检验。它不能给出总体用户成功率，也不能证明某个改动会提升可用性。

### 1.1 为什么用完整 clone 而不是 `tests/corpus/tsx`

`tests/corpus/tsx` 是票 02 的离线归档副本，**不含 `.git`**（`eval/fetch-corpus.ps1` 刻意不带历史）。它可以回答 T1 的路径，但不能回答 T2/T3 的“最近 500 个提交内的修改频率/最后修改时间”，也不能回答 T4 的双 commit diff。因此本包对 tsx 使用：

```
git clone https://github.com/privatenumber/tsx.git
git checkout 4473971f4b3261de253209b148d8fdc43269fcc4
```

clone 只放在被 `.gitignore` 忽略的 `out/` 下，不进主仓。

### 1.2 `tests/fixtures/history` 为什么不作为 T2/T3 样本

该 fixture 只有 6 个提交、2 个模块，无法产生“前 3 个高频模块”或“最早两个长期未动模块”的可区分答案。用它会让 key 退化成“两个模块都答对”，测不到目标行为。T2/T3 必须使用真实历史。

## 2. 任务与时间预算

| ID | 参与者要回答的问题（摘要，完整原话见脚本） | 主要视图 | 单题上限 | 通过判据（详见 `score-sheet.md`） |
| --- | --- | --- | --- | --- |
| T1 | 某入口到某目标符号的调用路径，经过哪些函数/模块/层 | 地图 + 路径播放 | 5 分钟 | 符号、模块、层序列全部正确且顺序正确 |
| T2 | 窗口内被改得最频繁的 3 个模块，并说明依据 | 演化时间线 | 5 分钟 | 3 个模块集合完全正确，无多报/错报 |
| T3 | 窗口内很久没有被改动的 2 个模块，并说明依据 | 演化时间线 | 5 分钟 | 2 个模块集合完全正确，无多报/错报 |
| T4 | 一次提交里新增/删除/修改了哪些模块 | 双 commit diff | 4 分钟 | 三类模块集合与类别归属全部正确，无多报/错报 |
| T5 | 被高亮/加粗的边代表什么；步进顺序是不是运行时执行顺序 | 地图 + 路径播放 | 2 分钟 | 两边都答“静态调用关系/最短静态调用链”，不得答数据流或执行顺序 |

**单场时间账：**

```
简报与同意             4 分钟
T1                     5 分钟
过渡                   1 分钟
T2                     5 分钟
过渡                   1 分钟
T3                     5 分钟
过渡                   1 分钟
T4                     4 分钟
过渡                   1 分钟
T5                     2 分钟
结束与设备复位         1 分钟
合计                  30 分钟
```

- 任务计时从主控念完任务文字开始，到参与者说出“答完了”为止。
- 过渡时间用于主控切窗口/复位数，不计入任务耗时。
- 超过单题上限：主控说“时间到，请给出你目前最好的答案，或者说不知道”，记 `timeout=true`；即使随后答对，也不计为通过。
- 超过 30 分钟硬上限：停止后续任务，未做任务记 `not-run`；已做任务照常评分；把超时写进证据，而不是静默补时。

**准备阶段不计入 30 分钟：** 时间线窗口首次加载的原记录为 **372.1 秒**（617 个刻度）。该读数**未记录构建类型，已失效，需在改后二进制上重测**；预热耗时必须以执行前实测为准。见 §3.5。

| T4 diff 窗口标题直接显示“新增/删除/修改”的数量 | `arch-view diff` | **不把数量作为得分项**；只评模块路径集合与类别归属。记录 `ui_leak_t4_counts=true` |
| T1 路径播放状态栏显示 `k/N`，N 是总步数 | `arch-view map` 路径模式 | **不把“共 N 步”作为独立得分项**；只评符号/模块/层序列。记录 `ui_leak_t1_step_count=true` |
| T2/T3 时间线图例显示 `churn 0→11+` | `arch-view timeline` | 这是产品 UI，不是主控泄题；记录 `ui_legend_visible=true`，不要额外解释指标 |
| T2/T3 底部显示 `lastModified` 的原始 epoch 数字 | `arch-view timeline` | 这是产品 UI；记录参与者是否把它当日期/看不懂。归因为 `V-TL` 或 `I-RECENCY` |

## 5. 通过、失败与归因（摘要）

- **通过** = 答案集合/序列与 key 完全一致，且未超时。部分分只用于诊断，不改变通过/失败。
- **失败**必须归入以下主类之一，并附视图标签（map / drill / path / timeline / diff / shell）：

| 主类 | 含义 | 典型证据 |
| --- | --- | --- |
| `V` 视图问题 | 元素存在，但看不清/看不懂/被误导 | 标签重叠、颜色饱和、原始 epoch、高亮对比度低、相机丢失、行被截断 |
| `I` 信息缺失 | 模型/产物里有，界面没给出 | 无全局排序/筛选、无日期格式化、无模块清单、无 diff 路径/原因 |
| `F` 动线问题 | 找不到入口/控件/视图，或跳转太多/回退迷路 | 首动作是乱点、找不到“播放/前进”、反复切视图、忘记当前刻度 |
| `S` 语义误读 | 图形语义理解错误 | 把边读成数据流、把步进读成运行时执行顺序 |
| `E` 环境 | 崩溃/卡死/加载失败/窗口不在屏内 | 录屏与日志；单独统计，不混入可用性缺陷 |
| `U` 任务歧义 | 任务措辞本身有歧义 | 需第二人复核；不计为参与者失败；记录后修正脚本，另起一轮 |

**协议失败判据（票 12）：**

| 条件 | 处理 |
| --- | --- |
| 任一任务通过率 `<4/5` | 该任务未达门槛；产出按视图归因的缺陷清单 |
| 答案 key 在首位参与者后被修改 | 本轮结果作废；修正另起一轮并保留旧 key |
| 单场超过 30 分钟且未记录 | 该场证据不完整；记录超时原因，不静默补时 |
| 证据缺失（无原话/无归因/无时间戳） | 该条失败不得进入缺陷清单；标 `unresolved` |
| 失败没有 `V/I/F/S/E` 主归因 | 视为未结案；不得用“用户不会用”替代 |

**结案红线：** 不允许用“用户不会用/用户没理解”作为主类结案。每个失败必须落到 `V/I/F/S/E` 之一；`U` 只在复核确认脚本歧义时使用。详细口径、部分分公式、置信度校准和 `out/usability.json` 字段见 `score-sheet.md`。

## 6. 这套测试能证明什么、不能证明什么

### 6.1 能证明

- 在**一个固定仓库、一个固定 commit、5 名筛选后的开发者、固定 30 分钟**下，5 个任务各自能否达到 `≥4/5`。
- 失败集中在哪个**视图**（地图/下钻/路径/时间线/diff）、哪类**信息**（排序、日期、路径清单）、哪段**动线**（入口、控件、回退）。
- 参与者“自评很确定但答错”的比例；这是比单纯答错更危险的失败模式（变化盲视/过度自信）。
- 答案 key 与读数可被第三人用同一命令复现；失败证据可回看录屏时间戳。
- 当前界面在**一个真实中型 TS 仓库的历史规模**（617 个 first-parent 提交）下的首屏/加载表现，至少是本次样本的实测值。

### 6.2 不能证明

- **不能做统计推断**：5 人不是随机样本；`4/5` 的置信区间仍然很宽，不能外推为“80% 的用户能完成”。报告只报 `k/5` 和原始观察，不报显著性。
- **不能外推到其他仓库/语言/规模**：只测了 tsx 一个 TS 仓库；没有 excalidraw，没有 monorepo 大仓，没有 JS-only 仓。
- **不能证明因果关系**：本包没有 A/B 条件（没有动画开/关对照、没有静态/动态对照），不能证明“动画提升了理解”。
- **不能验证 R1 粒子误读**：R1（粒子沿调用边流动）未实现；T5 用的是“当前边高亮/加粗”，不是移动点。原研究文档假设的“沿边移动的点被读成数据流”在本轮**未验证**。
- **不能证明 T2/T3 的指标定义是唯一正确的**：key 用“修改次数/改动量”和“最后修改时间”；换指标可能换答案。本包只冻结一种口径。
- **不能证明修复有效**：测试给出缺陷清单，不验证修复后的效果；需要同一协议再跑一轮。
- **不能验证键盘/无障碍/reduced-motion**：未设条件，未测。
- **不能验证大仓性能**：原记录 617 个刻度的首次加载为 372.1 秒（构建类型不明，已失效，需在改后二进制上重测）；更大仓库可能更慢，本包没有测。
- **不能替代真实上手支持**：主控不提示是刻意的；若产品打算提供 onboarding，本测试测的是“无 onboarding 的基线”，不是“有 onboarding 的上限”。

## 7. 已知偏差与未验证项

1. **任务数从 3 扩到 5。** 票 12 原文只列 T1–T3；用户 2026-11-08 明确要求 T1–T5。本包以用户口径为准，票 12 的 3 任务描述视为被覆盖。
2. **样本只覆盖 tsx。** 票 12 说“02 的两个样本仓”；本包只用 tsx（用户允许“tsx 或 fixture”）。excalidraw 未测，不能声称跨仓一致。
3. **T2/T3 很可能暴露“没有全局排序/最近修改视图”。** 当前时间线只能点选单个模块看 count/churn/lastModified，没有按指标排序或筛选。如果多数参与者无法在 5 分钟内完成，正确归因是 `I`（信息缺失）或 `V`（视图问题），不是 `U`（用户不会用）。这是本包预期要暴露的产品缺口，不是脚本错误。
4. **T3 依赖原始 epoch。** 底部 `lastModified` 显示的是 epoch 秒数，不是格式化日期；参与者可能无法把它读成“多久没动”。这是真实的界面问题，归因 `V-TL`/`I-RECENCY`。
5. **T5 是替代刺激。** 原研究文档的粒子/移动点问题在当前 UI 上不存在；本包把问题改为“被高亮/加粗的边”和“步进顺序”。结论只能说明当前边高亮/步进的语义误读，不能说明粒子方案的误读率。
6. **T1/T4 有界面级泄题。** T1 状态栏泄露总步数；T4 标题泄露三类数量。评分已排除这些泄露项，但无法让参与者“没看见”。记录中必须标记。
7. **时间线首次加载 372.1 秒（构建类型不明，已失效，需在改后二进制上重测）。** 原读数保留但不作为当前预算；预热耗时必须以执行前实测为准。原记录被排除在参与者 30 分钟之外，但会拉长测试日。当前没有缓存/增量加载，不能承诺更大仓库可用。
8. **5 人不是统计样本。** `≥4/5` 是产品门槛；不要写“80% 用户通过”。报告只报分数与观察。
9. **没有下钻专项任务。** 票 12 的归因视图包含“下钻”，但 T1–T5 只在必要时自然触发下钻；若参与者主动下钻并失败，记录为 `drill` 视图。没有独立的下钻任务，不能单列下钻通过率。
10. **没有 reduced-motion / 动画开关对照。** 当前默认动画关闭；T5 只测当前默认状态。不能证明“关掉动画更好/更差”。
